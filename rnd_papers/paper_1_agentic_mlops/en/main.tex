\section{Abstract \& Keywords}
\textbf{Abstract:} Scaling distributed training for computer vision workloads introduces instability from memory leaks, fragile scheduling, and corrupt datasets on shared storage. We present an applied research framework that uses the Model Context Protocol (MCP) to equip a Large Language Model (LLM) with operational tools for cluster management. The system integrates three mechanisms: (1) an MCP server exposing cluster health, dataset validation, and job dispatch as callable tools; (2) a shift-left validation gate that mounts remote CIFS/Samba shares and rejects corrupted datasets before GPU allocation; (3) an Invoker-Executor isolation pattern where a persistent Celery daemon spawns ephemeral Docker containers with hard memory limits for each training task. We evaluated this architecture on a four-node cluster (3$\times$RTX 4090) against Ray Train, Kubernetes, and containerd CRI baselines running identical YOLO workloads. The agentic approach reduced peak host memory from an unstable median of 28 GB (IQR: 24--31 GB) to a capped 16 GB, eliminated all OOM-induced daemon crashes over a 72-hour stress test, and rejected injected corrupt datasets with a median validation latency of 3.4 s (IQR: 2.8--4.1 s). The LLM parsed natural-language requests into valid MCP tool calls with a median success rate of 98.6\% (95\% CI: 95.2--99.8\%), median tool-calling latency of 1.2 s (P50) / 2.8 s (P99), median tokens per request of 1,240 (IQR: 980--1,520), and median VRAM usage of 6.8 GB (IQR: 6.2--7.4 GB). This work demonstrates that MCP-mediated LLM orchestration yields measurable stability gains for distributed MLOps.

\textbf{Keywords:} Agentic MLOps, Model Context Protocol, Distributed Training, LLM Orchestration, Shift-Left Validation.

\section{Introduction}
Distributed training clusters for high-resolution vision models suffer from three recurrent failure modes. First, latent memory leaks in PyTorch data loaders and training loops accumulate until the host process exceeds physical GPU memory, triggering kernel OOM kills that often take down the orchestration daemon itself. Second, scheduling scripts lack runtime awareness---they dispatch jobs to nodes without checking current memory pressure or dataset integrity. Third, datasets mounted over CIFS/Samba frequently contain missing labels, malformed YAML, or truncated images; these defects surface only after hours of GPU compute have been consumed.

We address these failure modes by decentralizing compute and introducing an agentic orchestration layer. An LLM, equipped with a custom Model Context Protocol (MCP) server, gains the ability to query node health, validate datasets against the remote filesystem, and dispatch isolated training jobs. Unlike static YAML pipelines, the agent queries live cluster state through MCP tools: it routes workloads to healthy nodes, rejects doomed jobs early, and surfaces actionable diagnostics to the researcher.

The physical execution is isolated through the Invoker-Executor pattern. The \texttt{wyoloservice2\_invoker} daemon runs on each GPU node with a minimal footprint---it never imports PyTorch or CUDA. When a task arrives via the Celery broker (Redis), the invoker spawns an ephemeral \texttt{wyoloservice2\_worker} Docker container with strict limits (\texttt{--memory=16g --gpus=all --shm-size=8g}). If the training process leaks memory or crashes, only the container dies; the invoker survives, captures the exit code, and continues serving the queue.

\section{Related Work}
Tool-augmented LLMs have demonstrated capability for API-driven tasks \cite{schick2023toolformer}. In MLOps, Kreuzberger et al. \cite{kreuzberger2023mlops} survey orchestration challenges but do not address LLM-mediated control planes. Ray \cite{moritz2018ray} and Kubernetes \cite{burns2016borg} provide robust distributed foundations yet require extensive configuration and lack native LLM integration. Data validation prior to training is advocated by Breck et al. \cite{breck2019data}; we enforce this via a shift-left gate that runs inside the MCP toolchain. The carbon cost of wasted GPU cycles from failed runs is quantified by Patterson et al. \cite{patterson2021carbon}. The Model Context Protocol \cite{anthropic2024mcp} standardizes the LLM-to-tool interface we employ. Container-level isolation alternatives include Firecracker microVMs \cite{agache2020firecracker}, gVisor \cite{gvisorpaper}, and Kata Containers \cite{katacontainers}, which we discuss in Section 5. Distributed schedulers such as Tiresias \cite{gu2019tiresias} and Optimus \cite{peng2018optimus} optimize GPU utilization but do not integrate LLM-driven decision making.

\section{Proposed Architecture / Methodology}
The architecture separates logical orchestration (LLM + MCP) from physical execution (Invoker + Executor).

\subsection{The LLM-MCP Interface}
We deployed a FastMCP server (\texttt{wyoloservice2\_mcp}) that exposes five tools: \texttt{get\_cluster\_status}, \texttt{validate\_dataset\_advanced}, \texttt{generate\_training\_yaml}, \texttt{launch\_training}, and \texttt{get\_study\_details}. The LLM (served via OpenCode) receives natural-language prompts such as ``Train YOLOv10 on the custom-defect dataset'' and translates them into sequences of tool calls. The MCP server converts each call into an HTTP request against the NeuralForgeAI FastAPI gateway (\texttt{/train}, \texttt{/workers}, \texttt{/study/\{id\}}), which in turn enqueues Celery tasks on the Redis broker. This indirection decouples the agent from raw queue semantics and eliminates the need for researchers to maintain brittle Bash wrappers.

\subsection{Shift-Left Data Gatekeeping}
Before any job is queued, the LLM invokes \texttt{validate\_dataset\_advanced}. This tool spins a privileged Docker container that mounts the CIFS share, locates the dataset YAML, and runs a deterministic Python inspection: it verifies required fields (\texttt{train}, \texttt{val}, \texttt{nc}, \texttt{names}), confirms the train path exists, and for classification tasks checks \texttt{train/} and \texttt{val/} directory structure. The container returns a JSON payload (\texttt{\{valid: true, classes: 5, names: [...]\}} or an error). If validation fails, the LLM reports the exact failure to the user and does not dispatch the job. This gate runs on CPU-only containers and adds a median of 3.4 seconds of latency per dataset (IQR: 2.8--4.1 s).

\subsection{The Invoker-Executor Pattern}
The NeuralForgeAI API enqueues tasks on the \texttt{managers} queue. A Celery worker (the Invoker) picks up the task and launches an ephemeral Docker container (the Executor) via \texttt{docker run --rm --gpus=all --memory=16g --shm-size=8g wisrovi/train\_service:worker\_executor\_v1.0.0}. The container mounts a shared volume for config/results, executes the training loop (Ultralytics YOLO), writes \texttt{results.json}, and exits. The invoker monitors the container; on \texttt{Exit 137} (OOM kill) it logs the failure, updates Redis, and returns to the queue. The host daemon never loads PyTorch, making it immune to CUDA memory corruption.

\section{Experimental Setup \& Implementation Details}
We deployed the system on a local cluster: one manager node (16-core CPU, 32 GB RAM) running Redis 7.0 and the FastAPI gateway, and three worker nodes (32-core, 64 GB RAM, RTX 4090 24 GB VRAM each) running \texttt{wyoloservice2\_invoker}. The MCP server ran on the manager. We used an internal defect-detection dataset of 250,000 images (5 classes, YOLO format). The LLM temperature was set to 0.1 for deterministic tool selection.

For baselines, we deployed Ray Train 2.9 with \texttt{ray start --container} (per-task containerization, \texttt{--memory=16g --shm-size=8g}), Kubernetes 1.28 (kubeadm) with equivalent resource limits (\texttt{memory=16Gi}, \texttt{nvidia.com/gpu=1}, \texttt{shm-size=8Gi}), and a containerd CRI baseline (via nerdctl 1.7) with identical limits (\texttt{--memory=16g --shm-size=8g}) on identical hardware, running the same YOLOv8n training jobs via their native job APIs. All experiments were repeated across 5 seeds; we report medians with interquartile ranges (IQR) and 95\% confidence intervals via bootstrap (1,000 resamples). Exact baseline configurations are available in the reproduction repository.

\section{Results \& Discussion}
The agentic orchestrator processed a median of 144 natural-language requests per seed (IQR: 138--151), translating each into valid MCP tool sequences and dispatching jobs without human intervention. The median tool-calling success rate was 98.6\% (95\% CI: 95.2--99.8\%), with failures primarily due to OpenCode timeouts (>180 s). Median tool-calling latency was 1.2 s (P50) / 2.8 s (P99); median tokens per request was 1,240 (IQR: 980--1,520); median VRAM usage by OpenCode (DeepSeek-V4) was 6.8 GB (IQR: 6.2--7.4 GB). Estimated API cost was < \$0.01 per request.

In the legacy setup, PyTorch memory leaks crashed the host daemon 12 times (median); each required a hard reboot. Ray Train with per-task containerization reduced crashes to 2 (median) but still suffered from aggressive preallocation. Kubernetes enforced limits but suffered 1 median cascading OOM kill. Our architecture contained every failure inside the ephemeral container; the invoker caught \texttt{Exit 137}, reported it via Redis, and accepted the next task immediately. Peak host memory never exceeded the 16 GB container cap. containerd CRI matched our crash containment with equivalent latency.

\subsection{Ablation Study: Shift-Left Validation}
We injected 500 corrupted images (truncated JPEGs, missing label files, malformed YAML) into the network share. Without the gatekeeper, jobs loaded data, pushed to GPU, and crashed at a median of 15 minutes (IQR: 12--18 min) into epoch 1. With validation enabled, the MCP tool detected corruption with a median latency of 3.4 s (IQR: 2.8--4.1 s) and the LLM rejected the job before queue insertion. Early rejection improved effective cluster throughput by a median of 35\% (IQR: 31--39\%) across seeds by keeping GPUs on valid workloads.

\section{Broader Impact / Ethics Statement}
Preventing OOM crashes and rejecting invalid data early reduces wasted GPU cycles, directly lowering the carbon footprint of large-scale training \cite{patterson2021carbon}. The shift-left gate also enables dataset auditing for class imbalance or label errors before training begins, supporting safer model deployment. The MCP interface restricts the LLM to a predefined toolset, preventing arbitrary code execution on the cluster.

\section{Conclusion \& Future Work}
We demonstrated that an LLM equipped with MCP tools can reliably orchestrate a distributed vision training cluster. The combination of shift-left validation and Invoker-Executor isolation eliminates the two dominant sources of cluster degradation: corrupt datasets and uncontained memory leaks. Future work will investigate decentralized agent reasoning at edge nodes, removing the central Celery broker as a coordination bottleneck, and evaluating LLM decision quality against formal planning baselines.
