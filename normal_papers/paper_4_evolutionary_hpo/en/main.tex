\section{Abstract \& Keywords}
\textbf{Abstract:} Hyperparameter optimization (HPO) for object detection models remains computationally expensive when using naive search strategies. We present a decoupled, fault-tolerant HPO architecture that separates the optimization state management (Optuna with Tree-structured Parzen Estimator) from the physical training execution (distributed GPU workers via Celery/Redis). The system uses a composite fitness function balancing mAP@0.5:0.95 against training time and augmentation complexity. We evaluate on MS COCO 2017 with YOLOv8-s across 1--8 GPUs, comparing against Random Search, Hyperband, BOHB, and Ray Tune baselines. The decoupled TPE approach achieves a median best mAP of 48.5 (95\% CI: 47.8--49.1) over 200 trials, converges at trial 62 (95\% CI: 58--67), and scales at 95.6\% efficiency (95\% CI: 93.2--97.1\%) at 8 GPUs. Wilcoxon signed-rank tests confirm statistically significant improvement over Random Search (p < 0.001) and Hyperband (p = 0.003). The architecture tolerates worker failures without corrupting the search state. Sensitivity analysis of fitness coefficients reveals a Pareto frontier between mAP, training time, and model complexity. Code and configuration available at \url{https://github.com/wisrovi/wyoloservice2_production}.

\textbf{Keywords:} Hyperparameter Optimization, Tree-structured Parzen Estimator, Distributed Computing, YOLO, Optuna, Celery, Fault Tolerance, Ray Tune.

\section{Introduction}
YOLO architectures \cite{redmon2016you, redmon2017yolo9000, redmon2018yolov3, bochkovskiy2020yolov4, wang2023yolov7, jocher2023ultralytics} dominate real-time object detection, but their performance is highly sensitive to hyperparameters: learning rate, momentum, weight decay, and augmentation probabilities (mosaic, mixup, copy-paste). The search space is high-dimensional, non-convex, and expensive to evaluate---each trial requires a full training run.

Traditional HPO methods face three practical limitations in distributed settings. (1) \textbf{Tight coupling}: Scripts that embed both search logic and training loops cannot survive worker failures without losing search state. (2) \textbf{Inefficient baselines}: Grid search and Random Search \cite{bergstra2012random} waste budget on poor configurations. Bayesian Optimization \cite{snoek2012practical} and TPE \cite{bergstra2011algorithms} improve sample efficiency but are often implemented as single-process controllers. (3) \textbf{Scaling bottlenecks}: Multi-fidelity methods like Hyperband \cite{li2017hyperband} and BOHB \cite{falkner2018bohb} require coordinated early-stopping across workers, adding orchestration complexity.

We address these by fully decoupling the search manager from compute workers. The manager (Optuna + PostgreSQL) proposes trials; workers (Celery + Docker) execute them; results flow back via Redis to PostgreSQL. This separation enables horizontal scaling, fault isolation, and use of any Optuna sampler (TPE, CMA-ES, NSGA-II) without modifying worker code.

\section{Related Work}
\subsection{Bayesian and Multi-Fidelity Optimization}
TPE models $p(x|y)$ and $p(x|\neg y)$ as density estimators over good/bad configurations \cite{bergstra2011algorithms}. Hyperband \cite{li2017hyperband} uses successive halving to allocate resources to promising trials. BOHB \cite{falkner2018bohb} combines both. Regularized evolution \cite{real2019regularized} applies population-based search to architecture spaces. Optuna \cite{akiba2019optuna} provides a unified framework with relational storage backends but leaves distributed execution to the user.

\subsection{Distributed MLOps for HPO}
Ray Tune \cite{moritz2018ray} integrates search algorithms with trial scheduling but couples the controller to the Ray runtime. Kubernetes-based operators (Katib, KubeFlow) add significant control-plane overhead. Our Celery/Redis approach is lighter: the broker is a standard message queue, workers are stateless Docker containers, and the Optuna study persists in PostgreSQL independently.

\section{Methodology}
\subsection{Decoupled Architecture}
The system comprises three layers (Figure \ref{fig:arch}):
\begin{enumerate}
    \item \textbf{Manager Node}: Runs Optuna study with TPE sampler (\texttt{TPESampler}, multivariate=True, group=True). Study state persists in PostgreSQL. On each \texttt{study.ask()}, the sampler proposes a configuration, which is serialized and pushed to a Redis-backed Celery queue (\texttt{gpus\_high/medium/low}).
    \item \textbf{Message Broker}: Redis 7.0 with priority queues. Tasks route to workers based on GPU availability tags.
    \item \textbf{Worker Pool}: N nodes running \texttt{wyoloservice2\_invoker} daemons. Each dequeues a task, launches an ephemeral \texttt{wyoloservice2\_worker} container with the trial config, and reports the fitness value back to PostgreSQL via a callback HTTP endpoint.
\end{enumerate}
Failure handling: If a worker crashes (OOM, power loss), the Celery task returns \texttt{Exit 137}; the manager marks the trial as \texttt{FAIL} in Optuna, and the sampler conditions on this observation. No search state is lost.

\subsection{Composite Fitness Function}
Industrial deployment requires balancing accuracy, training cost, and inference latency. We define fitness $F$ for a hyperparameter vector $x$ as:
\begin{equation}
F(x) = \alpha \cdot \text{mAP}_{0.5:0.95}(x) - \beta \cdot \log_{10}(T_{\text{train}}(x) + 1) - \gamma \cdot \Omega(x)
\label{eq:fitness}
\end{equation}
where:
\begin{itemize}
    \item $\text{mAP}_{0.5:0.95}(x)$: Validation mAP at trial completion (percentage, e.g., 48.5).
    \item $T_{\text{train}}(x)$: Total training time in hours for the configured epochs.
    \item $\Omega(x)$: Complexity penalty for expensive augmentations. $\Omega = \mathbb{I}[\text{mosaic}>0.5] + 2\mathbb{I}[\text{mixup}>0.2] + 3\mathbb{I}[\text{copy\_paste}>0.1]$.
    \item $\alpha=1.0$, $\beta=0.05$, $\gamma=0.01$ (determined via pilot sweeps; see Section \ref{sec:coeff}).
\end{itemize}
The log penalty on time ensures that a 10$\times$ slower run (e.g., 20 hrs vs 2 hrs) costs only $\beta \cdot 1.3 \approx 0.065$ fitness points, while a 1 mAP gain yields 1.0. This forces TPE to prefer configurations that achieve high mAP quickly.

\subsection{Coefficient Justification}
\label{sec:coeff}
We ran a 50-trial pilot with $\alpha\in\{0.5,1.0,2.0\}$, $\beta\in\{0.01,0.05,0.1\}$, $\gamma\in\{0.005,0.01,0.02\}$. The chosen values ($\alpha=1.0, \beta=0.05, \gamma=0.01$) produced the highest correlation between fitness rank and final mAP on a held-out validation set, while keeping average trial time below 2 hours. Larger $\beta$ over-penalized slow runs, causing TPE to converge to fast but low-mAP configurations. Larger $\gamma$ suppressed all augmentations, reducing peak mAP by ~1.2 points.

\section{Experimental Setup}
\textbf{Dataset}: MS COCO 2017 (118k train, 5k val). \textbf{Model}: YOLOv8-s (Ultralytics \cite{jocher2023ultralytics}). \textbf{Hardware}: 8$\times$ NVIDIA A100 80 GB (primary); for reproducibility, we also report results on 3$\times$ RTX 4090 24 GB with gradient accumulation (4$\times$) to simulate 80 GB VRAM---we note this simulation lacks NVLink interconnect and full tensor core utilization, so absolute timings differ; scaling trends are comparable. \textbf{Software}: Optuna 3.4, Celery 5.3, Redis 7.0, PostgreSQL 15, Docker 24.0, Ray 2.9 (for Ray Tune baseline). \textbf{Budget}: 200 trials per method. \textbf{Epochs per trial}: 50 (early stopping patience=10 on fitness). \textbf{Seeds}: 10 independent runs per method; we report medians with interquartile ranges (IQR) and 95\% confidence intervals via bootstrap (1,000 resamples).

TPE finds a superior configuration (median +2.4 mAP over Random Search, 95\% CI: +1.7--+3.1) and converges 3$\times$ faster in trial count. The temporal penalty in Equation \ref{eq:fitness} steers search away from heavy-augmentation configs, reducing average trial time to 1.8 h. BOHB's multi-fidelity approach is competitive but requires implementing the \texttt{SHA} protocol in workers; our decoupled design achieves similar wall-clock time with simpler worker logic. Ray Tune with native TPE backend achieves comparable results (48.1 mAP, p = 0.18 vs. ours), confirming that the decoupled architecture's advantage lies in fault tolerance and operational simplicity rather than raw optimization performance. Wilcoxon signed-rank tests (paired across seeds) confirm statistically significant improvement over Random Search (p < 0.001) and Hyperband (p = 0.003); the difference vs. Ray Tune is not statistically significant (p = 0.18).

\subsection{Sensitivity Analysis and Pareto Frontier}
We swept $\alpha \in \{0.5, 1.0, 2.0\}$, $\beta \in \{0.01, 0.05, 0.1\}$, $\gamma \in \{0.005, 0.01, 0.02\}$ across 27 configurations (50 trials each, 5 seeds). Figure \ref{fig:sensitivity} shows the Pareto frontier of (mAP, training time, complexity). The chosen values ($\alpha=1.0, \beta=0.05, \gamma=0.01$) lie on the convex hull: increasing $\beta$ beyond 0.05 over-penalizes slow runs, causing convergence to fast but low-mAP configurations (median mAP drops to 46.8 at $\beta=0.1$); increasing $\gamma$ beyond 0.01 suppresses all augmentations, reducing peak mAP by ~1.2 points. The sensitivity heatmap (Appendix \ref{app:sensitivity}) shows fitness rank correlation with final mAP remains > 0.85 across a broad region around the chosen coefficients.

\subsection{Search Space Coverage and Diversity}
Across 10 seeds, the decoupled TPE explored a median of 87\% (IQR: 84--90\%) of the discrete \texttt{imgsz} choices and 92\% (IQR: 89--94\%) of batch size choices. Continuous parameter coverage (lr, momentum, weight decay, augmentation probs) measured via kernel density estimation showed median coverage of 78\% (IQR: 74--82\%) of the sampled hypervolume. Config diversity, measured by mean pairwise Euclidean distance in normalized parameter space, was 0.42 (IQR: 0.39--0.45), indicating broad exploration before convergence.

\section{Conclusion \& Future Work}
We demonstrated a decoupled, fault-tolerant HPO system for YOLO using Optuna TPE, Celery, and Docker. The composite fitness function balances accuracy, speed, and complexity. Results on COCO show +2.4 mAP over Random Search with 3$\times$ faster convergence and 95.6\% scaling efficiency at 8 GPUs. Future work: integrate BOHB-style multi-fidelity into the decoupled framework, and explore multi-objective search (mAP vs. latency vs. model size) with NSGA-II.
