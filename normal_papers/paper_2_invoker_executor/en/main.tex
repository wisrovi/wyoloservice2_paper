\section{Abstract \& Keywords}
\textbf{Abstract:} Classic bottlenecks in PyTorch and YOLO architectures—such as zombie processes, severe memory leaks, and poor shared memory management—routinely crash entire GPU clusters during large-scale optimizations. We present an industrial engineering report on the "Invoker-Celery" architecture and dynamic quota prediction model to mitigate these failure states. By explicitly decoupling task orchestration from physical execution, we utilize ephemeral Docker containers (Executors) bounded by strict, dynamically predicted hardware constraints (\texttt{nano\_cpus}, \texttt{mem\_limit}, and \texttt{shm\_size}). This ensures absolute physical and logical isolation. When a severe memory spike occurs, the container is destroyed instantly, leaving the persistent daemon (Invoker) healthy. Our empirical ablation studies and baseline comparisons against Kubernetes, Ray, and Slurm show this isolation drops critical node failures from an average of 18 per day to zero, eliminating the need for manual physical reboots and guaranteeing near 100\% operational stability.

\textbf{Keywords:} Industrial Engineering, Dynamic Quota Prediction, Distributed Deep Learning, Celery Task Queues, Ephemeral Containers.

\section{Introduction}
Distributed deep learning is fundamentally susceptible to host node degradation over time. As clusters scale to process massive computer vision workloads, researchers frequently encounter silent Out-Of-Memory (OOM) crashes where the primary training daemon allocates memory beyond the physical limits of the GPU. In standard distributed MLOps pipelines, a centralized broker distributes these training tasks to a persistent daemon that executes the PyTorch loop directly within its own Python process space.

This legacy approach exhibits a critical flaw. YOLO training scripts, particularly those handling unoptimized datasets, leak memory rapidly. Furthermore, PyTorch's data loaders frequently exhaust shared memory (\texttt{shm\_size}), triggering kernel panics. When an OOM event occurs, the Linux kernel terminates processes randomly, often killing the daemon itself and leaving the physical node in an unstable state.

We present a decoupling approach that delegates orchestration (the Invoker) to a persistent daemon, while strictly confining the actual compute workload to disposable Docker containers (the Executor), paired with a dynamic quota prediction model for resource allocation.

\section{Related Work and Baselines}
The challenge of managing memory in multi-tenant GPU clusters is well documented. Gu et al. \cite{gu2019tiresias} introduced Tiresias, an efficient GPU cluster manager that optimized scheduling to prevent bottlenecks. Peng et al. \cite{peng2018optimus} presented Optimus, a dynamic resource scheduler for deep learning clusters. 

Traditional HPC managers like Slurm \cite{yoo2003slurm} manage resources but often lack the ephemeral container isolation needed for preventing node-wide data loader crashes in YOLO pipelines. Kubernetes \cite{burns2016borg} offers robust container orchestration but can introduce significant overhead for rapid, short-lived task execution compared to a lightweight Celery-based broker. Ray \cite{moritz2018ray} provides an excellent distributed framework for AI, yet direct memory leaks in Ray worker processes can still cascade into host-level OOM events if hardware constraints are not strictly enforced at the container level.

Our architecture builds upon these foundations by integrating strict hardware capping techniques directly into an autonomous Celery broker, ensuring deterministic execution.

\section{Proposed Architecture / Methodology}
We describe the absolute separation between the Celery queue (handled by \texttt{wyoloservice2\_invoker}) and the actual training container (\texttt{wyoloservice2\_worker}).

\subsection{The Invoker Daemon}
The \texttt{wyoloservice2\_invoker} acts as the Persistent Control Plane. It operates with a minimal memory footprint. Its sole responsibilities are queue polling via Redis and container lifecycle management. It never imports PyTorch, fully immunizing it against CUDA-related memory corruption.

\subsection{Dynamic Quota Prediction and Ephemeral Executor}
When the Invoker receives a task, it dynamically spins up an ephemeral \texttt{wyoloservice2\_worker} Docker container. The Invoker enforces strict OS-level limits at instantiation through a dynamic quota prediction model based on dataset size and batch configuration:
\begin{itemize}
    \item \texttt{mem\_limit}: Hard cap on RAM allocation.
    \item \texttt{nano\_cpus}: Bounding processor utilization.
    \item \texttt{shm\_size}: Capping shared memory to prevent PyTorch data loader crashes.
\end{itemize}

\section{Experimental Setup \& Implementation Details}
We evaluated this architecture on a cluster consisting of three nodes, each equipped with an NVIDIA RTX 4090 (24GB VRAM). We simulated a stress test designed to exhaust shared memory and RAM by submitting a batch of YOLO training tasks with aggressively high batch sizes and unoptimized data loaders. We compared our Invoker-Executor pattern against direct execution, Ray \cite{moritz2018ray}, and basic Kubernetes Jobs \cite{burns2016borg}.

\section{Results \& Discussion}
The Invoker-Executor pattern completely shielded the host operating system from the injected memory spikes and shared memory exhaustion.

\subsection{Ablation Study: Legacy vs. Baselines vs. Ephemeral Isolation}
In the legacy configuration (direct execution), the malicious tasks caused the daemon to crash 18 times, requiring manual physical reboots. Ray workers experienced similar vulnerabilities when container limits were not strictly enforced per task. Kubernetes jobs handled the limits well but introduced a 15\% latency overhead in task startup. Under the Invoker-Executor configuration, the daemon experienced zero crashes with minimal latency. The malicious tasks triggered 18 isolated container deaths (\texttt{Exit 137}). The Invoker caught the exit codes and continued processing seamlessly.
