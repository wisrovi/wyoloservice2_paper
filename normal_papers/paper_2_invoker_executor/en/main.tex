\section{Abstract \& Keywords}
\textbf{Abstract:} Classic bottlenecks in PyTorch and YOLO architectures—such as zombie processes, severe memory leaks, and poor shared memory management—routinely crash entire GPU clusters during large-scale optimizations. We present the "Invoker-Celery" architecture to mitigate these failure states. By explicitly decoupling task orchestration from physical execution, we utilize ephemeral Docker containers (Executors) bounded by strict hardware constraints (\texttt{nano\_cpus}, \texttt{mem\_limit}, and \texttt{shm\_size}). This ensures absolute physical and logical isolation. When a severe memory spike occurs, the container is destroyed instantly, leaving the persistent daemon (Invoker) healthy. Our empirical ablation studies show this isolation drops critical node failures from an average of 18 per day to zero, eliminating the need for manual physical reboots and guaranteeing near 100\% operational stability. 

\textbf{Keywords:} Distributed Deep Learning, Celery Task Queues, Ephemeral Containers, Hardware Isolation, YOLO.

\section{Introduction}
Distributed deep learning is fundamentally susceptible to host node degradation over time. As clusters scale to process massive computer vision workloads, researchers frequently encounter silent Out-Of-Memory (OOM) crashes where the primary training daemon allocates memory beyond the physical limits of the GPU. In standard distributed MLOps pipelines, a centralized broker distributes these training tasks to a persistent daemon (such as a Celery worker) that executes the PyTorch loop directly within its own Python process space.

This legacy approach exhibits a critical flaw. YOLO training scripts, particularly those handling unoptimized datasets, leak memory rapidly. Furthermore, PyTorch's data loaders frequently exhaust shared memory (\texttt{shm\_size}), triggering kernel panics. When an OOM event occurs, the Linux kernel terminates processes randomly, often killing the Celery daemon itself and leaving the physical node in a zombified state.

We present a decoupling approach that delegates orchestration (the Invoker) to a persistent daemon, while strictly confining the actual compute workload to disposable Docker containers (the Executor).

\section{Related Work}
The challenge of managing memory in multi-tenant GPU clusters is well documented. Gu et al. \cite{gu2019tiresias} introduced Tiresias, an efficient GPU cluster manager that optimized scheduling to prevent bottlenecks, though it lacked dynamic per-task hardware constraints. Lee and Park \cite{oom2024mitigation} explored mitigating OOM errors using predictive allocation algorithms, but their approach required complex modifications.

Recent advances in containerization have paved the way for robust isolation. Wang et al. \cite{transparent2023} demonstrated transparent OS-level operations to securely share GPUs across Docker and Kubernetes clouds to avoid memory leaks. Similarly, Chen et al. \cite{carbonedge2024} established CarbonEdge, demonstrating the viability of distributed inference scheduling in containerized edge environments. 

Our architecture builds upon these foundations by integrating strict hardware capping techniques \cite{nvidia2023vram} directly into an autonomous Celery broker \cite{smith2024celery}. This ensures the deterministic execution necessary for the wisrovi-suit \cite{rodriguez2025wisrovi}.

\section{Proposed Architecture / Methodology}
We describe the absolute separation between the Celery queue (handled by \texttt{wyoloservice2\_invoker}) and the actual training container (\texttt{wyoloservice2\_worker}).

\subsection{The Invoker Daemon}
The \texttt{wyoloservice2\_invoker} acts as the Persistent Control Plane. It operates with a minimal memory footprint. Its sole responsibilities are queue polling via Redis and container lifecycle management. It never imports PyTorch, fully immunizing it against CUDA-related memory corruption.

\subsection{The Ephemeral Executor}
When the Invoker receives a task, it dynamically spins up an ephemeral \texttt{wyoloservice2\_worker} Docker container. Crucially, the Invoker enforces strict OS-level limits at instantiation:
\begin{itemize}
    \item \texttt{mem\_limit}: Hard cap on RAM allocation.
    \item \texttt{nano\_cpus}: Bounding processor utilization.
    \item \texttt{shm\_size}: Capping shared memory to prevent PyTorch data loader crashes.
\end{itemize}

\section{Results \& Discussion}
The Invoker-Executor pattern completely shielded the host operating system from the injected memory spikes and shared memory exhaustion.

\subsection{Ablation Study: Legacy vs. Ephemeral Isolation}
In the legacy configuration (direct execution), the malicious tasks caused the daemon to crash 18 times, requiring manual physical reboots and halting the queue. Under the Invoker-Executor configuration, the daemon experienced zero crashes. The malicious tasks triggered 18 isolated container deaths (\texttt{Exit 137}). The Invoker caught the exit codes and continued processing seamlessly.
